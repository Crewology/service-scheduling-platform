# Development Preview Rate-Limit Diagnostics

## Confirmed Cause

The recurring plain-text page `Too many requests. Please try again later.` is generated by the managed development-preview gateway, not by OlogyCrew's Express application.

The diagnosis is conclusive because the affected public preview request returned the plain-text message while the local application returned `200 OK` at the same time. The request did not appear in OlogyCrew's network, browser-console, or server request logs. The message also does not exist in the current application source. OlogyCrew's own limiter returns a structured JSON payload with code `RATE_LIMITED` and different recovery text.

A sustained verification sent 1,250 read requests directly to the development application; all 1,250 returned `200`. A separate burst of 20 requests through the public preview gateway returned 7 successful responses and 13 upstream `429` responses. Successful gateway responses carried `X-OlogyCrew-Origin: application`; the plain-text throttled response did not reach the application. This isolates the recurring message to the managed preview gateway.

## Permanent Application Safeguard

OlogyCrew now applies its broad read limiter only in production. Development retains the stricter write and sensitive-endpoint limiters, while the managed preview gateway remains responsible for its own upstream development protection. This prevents double-throttling during intensive preview, screenshot, and navigation testing without reducing production abuse protection.

Every response that reaches OlogyCrew includes `X-OlogyCrew-Origin: application`. If a future error response lacks that header and is absent from application logs, it originated upstream of the project.

## Recovery

An upstream preview-gateway block is temporary. Wait briefly, then reload the preview. Production traffic on OlogyCrew.com is governed by the separate production application policy and is not changed by this development-only safeguard.

## Vite Hot-Reload WebSocket

The development-only console error `[vite] failed to connect to websocket (WebSocket closed without opened)` has the same upstream cause. Vite is correctly attached to OlogyCrew's HTTP server, and both the local server and the preview gateway return a valid `101 Switching Protocols` WebSocket handshake when the gateway is available. The latest disconnect occurred without an OlogyCrew or Vite server restart, while the preview gateway was also intermittently returning its plain-text `429` page.

After the gateway cooldown, the same development URL loaded normally and the browser console was clear. No alternate HMR host, port, or path should be forced in project code: the current same-server setup is correct, and changing it would bypass the managed preview routing contract.

This error cannot affect the published site. Production contains no `/@vite/client` reference and does not run Vite HMR. It is also unrelated to OlogyCrew's application SSE messaging, which uses `/api/sse/notifications` and remains unchanged.
